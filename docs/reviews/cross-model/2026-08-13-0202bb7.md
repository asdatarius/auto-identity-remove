## Summary

I reviewed all requested files end to end, focusing on PII flow, success accounting, scheduler/state durability, and dashboard exposure paths. I found four P1 issues: one direct PII leak to logs, two false-success/wrong-person submission paths in the generic runner, and one setup path that recreates plaintext PII beside an encrypted config while silently leaving runtime on the old encrypted data.

### Detail

#### 1. [P1] Raw form values are written to logs on select mismatches

- **Location:** `lib/forms.js:135`
- **What:** When a `<select>` field cannot match either by label or by value, the warning logs the exact submitted `value`. In this tool those values include name, email, state, zip, and country-derived fields.
- **Trigger:** Any broker form with a select whose options do not exactly match the configured value, such as a renamed state/country selector or an international postal/region form.
- **Impact:** User PII is emitted to stdout/stderr and can then land in run logs or the dashboard's live stream, violating the tool's primary privacy goal.
- **Fix:** Do not log raw field contents. Log only the selector and a redacted field class, or redact all values before logging.
- **Disposition:** fixed (lib/forms.js - value withheld, length only; test/pii-not-logged.test.js)

#### 2. [P1] Generic runner records success after only clicking a “Do Not Sell” link

- **Location:** `generic-runner.js:370`
- **What:** After `clickDoNotSell(page)` returns true, the code calls `fillGenericForm()` and `submitForm()` but ignores whether either actually succeeded, then unconditionally returns `finalize('Do Not Sell clicked')`. `runGenericBrokers()` later records that as success.
- **Trigger:** A generic broker page with a visible “Do Not Sell” link/button that merely opens another page, modal, or form, but where no opt-out was actually submitted or toggled.
- **Impact:** The tool reports the broker as removed and suppresses retries for 90 days even though no request may have left the machine.
- **Fix:** Treat this path as success only if a concrete submit/preference-change signal is observed; otherwise return `manual` or a distinct non-success status.
- **Disposition:** fixed (generic-runner.js - requires a real submit or a confirmation page, else manual; test/generic-runner-false-success.test.js)

#### 3. [P1] Generic broker submissions always use `persons[0]` and collapse state across people

- **Location:** `generic-runner.js:209`
- **What:** `activePerson()` hardcodes the first entry of `config.persons`, and the generic-runner skip/write paths key state by bare `broker.name` rather than `stateKey()`. In multi-person configs, later people do not get their own generic-broker submissions or state.
- **Trigger:** A config using `persons` with more than one person, plus any generic broker flow that fills name/email fields.
- **Impact:** One person's PII is sent during another person's run, and additional people can be marked skipped/removed without their own submission ever being made.
- **Fix:** Pass the current person and total person count into the generic runner, derive field values from that person, and use `stateKey()` consistently for reads and writes.
- **Disposition:** fixed - the generic pass now runs once per person and keys state via stateKey(name, person, count), the same composite key the explicit brokers already used. fillGenericForm() takes the person explicitly. Cost accepted deliberately: an N-person run does the ~490-broker pass N times, so wall-clock scales with N. test/generic-runner-per-person.test.js

#### 4. [P1] Rerunning setup on an encrypted install recreates plaintext config and leaves runtime on stale encrypted data

- **Location:** `setup.js:117`
- **What:** Setup only loads existing plaintext `config.json`. If the installation already uses `config.json.enc`, setup starts from empty values, writes a fresh plaintext `config.json`, and only re-encrypts if the user explicitly opts in again. Meanwhile runtime still prefers `config.json.enc` in `loadConfig()`.
- **Trigger:** User runs `node setup.js` after previously encrypting the config, intending to update PII, credentials, or schedule settings.
- **Impact:** Full PII and secrets are written back to disk in plaintext, and the user's edits may be ignored at runtime because the tool continues loading the old encrypted config.
- **Fix:** Make setup load through `loadConfig()`/`isConfigEncrypted()`, require the passphrase when editing an encrypted install, and rewrite the encrypted config in place instead of emitting plaintext by default.
- **Disposition:** fixed (setup.js readExistingConfig - decrypts existing values, refuses to overwrite a locked encrypted config, re-encrypts instead of emitting plaintext; test/setup-encrypted-rerun.test.js)

## Maintainer notes

Every finding above was verified against the code before being acted on, as
docs/CROSS_MODEL_REVIEW.md requires. All four were real.

Finding 3 was initially deferred as a product tradeoff and then fixed properly on
the maintainer's call. It was not a code slip: watcher.js deliberately ran the
generic pass once, outside the persons loop, with a comment saying so in three
places. The reviewer was right that form-filling generic brokers therefore covered
only persons[0] while state was keyed on the bare broker name, so the entry read
as done for the whole household.

The fix runs the generic pass once per person and keys state with
stateKey(name, person, count) - the composite key the explicit brokers already
used, so single-person state files are byte-compatible and do not resubmit. The
accepted cost: an N-person monthly run now does the ~490-broker pass N times, so
wall-clock scales with N. Domain-level toggles (cookie / "Do Not Sell") get
re-applied per person, which is harmless.
